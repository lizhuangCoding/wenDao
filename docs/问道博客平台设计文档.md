## 1. 项目概述

### 1.1 项目目标

构建一个以技术内容为核心的个人博客平台，支持：

- 文章发布、编辑、分类与合集管理
- 用户注册、登录、GitHub OAuth 登录
- 两级评论互动、点赞/点踩
- 站内通知系统
- 基于 RAG 的多智能体 AI 对话问答（ThinkTank）
- AI 写作辅助
- 知识文档审核入库
- 博主后台管理
- 验证码邮箱服务（注册验证、密码重置）

当前项目已经从早期设计演进为**前后端分离架构**：前端是 React 单页应用，后端是 Gin API 服务。

### 1.2 核心特性

- **文章管理**: Markdown 文章创作、草稿/发布/定时发布、封面图、正文图片上传（版权水印）、活跃度排序
- **合集管理**: 文章合集/系列，支持有序排列与上一篇/下一篇导航
- **用户系统**: 邮箱注册/登录、GitHub OAuth 登录、个人中心头像上传、评论邮件通知偏好
- **评论系统**: 两级评论、点赞/点踩、普通用户删除自己的评论、管理员删除/恢复评论、评论回复邮件通知
- **站内通知**: 评论回复通知、管理员广播通知
- **AI 对话**: 登录用户可在独立页面进行 AI 问答（多智能体 ThinkTank 编排），并持久化对话历史，支持分享与导出
- **AI 写作**: 管理员可使用 AI 润色、扩展、缩短、SEO 标题生成
- **知识文档**: 外部 URL 内容抓取入库，审核后可转为已发布文章
- **后台管理**: 文章、分类、合集、评论、用户管理、知识文档、统计、设置
- **文件上传**: 统一上传模块，支持图片压缩、版权水印、未引用文件清理
- **速率限制**: 基于 Redis 的多级别限流（全局/IP/用户）
- **3D 文章轨道**: 基于语义嵌入和 UMAP 降维的文章知识图谱

### 3.1 架构说明

当前采用分层架构：

```text
React SPA → Gin API → Service → Repository → MySQL / Redis / Redis Vector
```

### 3.2 分层职责

- **Handler 层**: 参数接收与校验、调用 Service、错误语义匹配、返回统一响应
- **Service 层**: 业务编排、领域逻辑、返回 `svcerrors` 包中定义的语义化错误
- **Repository 层**: 数据查询与持久化
- **Model 层**: GORM 模型定义
- **Middleware 层**: 认证（Required/Optional/Admin）、CORS、速率限制、安全头部、日志、Panic 恢复
- **前端 API 层**: Axios 统一请求入口
- **前端 Store 层**:
  - Zustand 管理 auth、chat、theme、UI 等本地状态
  - React Query 管理文章、分类、合集、通知等服务端数据缓存

### 3.3 依赖注入说明

当前项目没有使用 Wire 等 DI 框架。依赖装配由 `backend/cmd/server/bootstrap_services.go` 和 `bootstrap_http.go` 手工完成。

### 3.4 错误处理规范

所有服务层返回的语义化错误统一在 `internal/svcerrors/svcerrors.go` 中定义，按域分为六大类：

- **Article**: `ErrArticleNotFound`、`ErrCategoryNotFound`、`ErrArticleAlreadyPublished`、`ErrArticleAlreadyDraft`
- **Category**: `ErrSlugAlreadyExists`、`ErrCannotDeleteCategoryWithArticles`
- **Comment**: `ErrCannotCommentOnUnpublishedArticle`、`ErrParentCommentNotFound`、`ErrParentCommentNotBelongToArticle`、`ErrCannotReplyToDeletedComment`、`ErrCannotReplyToReplyComment`、`ErrCommentNotFound`、`ErrPermissionDenied`、`ErrCommentAlreadyDeleted`、`ErrCommentIsNotDeleted`
- **Collection**: `ErrCollectionNotFound`、`ErrInvalidCollectionStatus`、`ErrCannotDeleteCollectionWithArticles`
- **User**: `ErrUserNotFound`、`ErrEmailAlreadyExists`、`ErrInvalidEmailOrPassword`、`ErrAccountBanned`、`ErrUsernameAlreadyExists`
- **Upload**: `ErrFileTypeNotAllowed`、`ErrFileSizeExceedsLimit`

Handler 层通过 `errors.Is(err, svcerrors.ErrXxx)` 匹配语义化错误，返回对应的 HTTP 状态码和用户提示。

## 6. 认证与用户系统设计

### 6.1 认证模式

当前项目使用 **Access Token + Refresh Token** 双 token 体系：

- **Access Token**: 短期有效（默认 1 小时）
- **Refresh Token**: 用于刷新 Access Token（默认 7 天），支持轮转
- **黑名单机制**: Redis 用于失效旧 token（logout 时加入黑名单）

### 6.2 Token 传输方式

混合式实现：

- 前端将 access token 写入本地存储，通过 `Authorization: Bearer ...` 发起部分请求
- 后端也支持通过 Cookie 读取 token
- refresh token 主要由 HttpOnly Cookie 管理

### 6.3 中间件认证级别

- `AuthRequired` — 需要有效 JWT
- `AuthOptional` — 注入用户上下文（若有效 token 存在），否则通过（用于评论点赞/点踩）
- `AdminRequired` — 需要 admin 角色

### 6.4 用户系统能力

当前已实现：

- 邮箱注册（含验证码校验）
- 邮箱登录
- GitHub OAuth 登录
- 获取当前用户资料
- 登出
- 个人中心头像上传
- 修改用户名
- 评论回复邮件通知偏好设置
- 管理员：用户列表、修改角色、封禁/解封

### 6.5 GitHub OAuth 登录

GitHub OAuth 设计已形成闭环：

1. 前端登录页/注册页点击 GitHub 登录
2. 跳转后端 `/api/auth/github`
3. 后端生成 `state` 并跳 GitHub 授权页
4. GitHub 回调后端 `/api/auth/github/callback`
5. 后端完成登录、写入 Cookie、跳回前端 `site.url`
6. 前端启动时主动调用 `/api/auth/me` 恢复登录态

详细说明见：`docs/2026-04-13-github-oauth-login-design.md`

### 6.6 用户头像策略

当前头像来源分为：

- `default`: 系统默认头像（DiceBear 生成）
- `github`: GitHub 头像
- `custom`: 用户自行上传头像

同步规则：

- GitHub 新用户默认使用 GitHub 头像
- 后续 GitHub 登录时：
  - 如果当前头像来源是 `github` 或 `default`，同步最新 GitHub 头像
  - 如果当前头像来源是 `custom`，不覆盖

### 6.7 验证码邮件系统

通过 SMTP 邮件发送验证码，场景包括：

- `POST /api/auth/register/code` — 发送注册验证码
- `POST /api/auth/password-reset/code` — 发送密码重置验证码
- `POST /api/auth/password-reset/confirm` — 验证码 + 新密码确认重置

## 9. AI / RAG 设计

### 9.1 ThinkTank 多智能体架构

当前 AI 对话采用 ThinkTank 多智能体编排系统，包含：

- **Librarian（图书管理员）**: 本地 RAG 检索 agent，负责从文章向量库中检索相关内容
- **Journalist（记者）**: 网络搜索 agent，负责从网络获取实时信息
- **Synthesizer（编辑）**: 答案合成 agent，综合多个来源的信息生成最终回答
- **Intent Reviewer（意图审核）**: 判断用户意图并决策搜索策略

工作流程：

```
用户提问 → Intent Reviewer 意图分析
         → Librarian 本地检索（RAG）
         → Journalist 网络搜索（如需要）
         → Synthesizer 答案合成
         → 流式输出（SSE）
```

**特点**：
- 支持 Google ADK 集成和手动流程回退两种模式
- 运行状态持久化（支持对话中断后恢复）
- 对话记忆压缩（长对话自动摘要，保留上下文）
- 每个 agent 的步骤日志可追溯

### 9.2 RAG 检索

基于 eino 框架实现：

- **Embedder**: Doubao Embedding Large 模型进行文本向量化
- **Vector Store**: Redis Stack 实现 HNSW 索引 + 余弦相似度搜索
- **Retriever**: 相似度阈值过滤（`rag_min_score`）+ Top-K 结果
- **向量同步**: 后台服务自动同步已发布文章的向量索引

### 9.3 向量索引状态

文章 `ai_index_status` 字段管理：

- `pending` — 待索引
- `success` — 索引成功
- `failed` — 索引失败

### 9.4 3D 文章轨道（知识图谱）

基于语义嵌入的 3D 文章可视化：

1. 对已发布文章提取语义嵌入向量
2. 使用 UMAP 降维到 3D 坐标（X、Y、Z）
3. 计算语义邻居关系
4. 前端渲染 3D 空间下的文章位置关系

## 10. 文件上传设计

### 10.1 统一上传模块

当前上传体系由统一的上传服务负责：

- 文件大小校验（`MaxSize` 限制）
- MIME 类型校验（通过 `http.DetectContentType` 检测真实类型）
- 图片压缩与缩放（JPEG 质量编码、PNG 最佳压缩、`MaxImageWidth/Height` 缩放）
- 版权水印（文章图片用右下角水印，封面图用居中水印，头像无水印）
- 本地落盘（`/uploads/YYYY/MM/{hash}_{timestamp}.{ext}`）
- 记录 `uploads` 表元数据

### 10.2 水印系统

三种水印模式：

- `ModeNone` — 无水印（头像上传）
- `ModeText` — 右下角 "lizhuang" 版权文字（文章正文图片）
- `ModeTile` — 居中覆盖水印（封面图，防止裁剪后不可见）

### 10.3 安全策略

- 只允许图片 MIME 类型
- 服务器根据文件内容探测真实 MIME（不信任客户端声明）
- 存储时使用服务端决定的安全扩展名
- 存储路径位于 `/uploads/...`
- 上传文件通过静态资源路径对外访问
- 路径穿越防护（`managedUploadDiskPath` 验证）

### 10.4 未引用文件清理

后台定时任务清理数据库中确认未引用且超过保留期（默认 2 天）的上传文件。

### 10.5 使用场景

- 后台文章正文图片上传（含版权水印）
- 封面图片上传（含居中水印）
- 用户头像上传（无水印）

## 13. 安全设计

### 13.1 认证安全

- Access / Refresh 双 token 体系
- Refresh Token 轮转
- Redis 黑名单失效旧 token
- GitHub OAuth 使用 `state` 做 CSRF 防护
- 敏感 Cookie 使用 HttpOnly，release 模式下启用 Secure

### 13.2 速率限制

基于 Redis 的多级别限流（滑动窗口计数器算法）：

- `Global` — 全局共享
- `IP` — 基于客户端 IP
- `User` — 基于认证用户 ID（未认证回退到 IP）

限流路由：

| 限流器名称 | 类型 | 限制 |
|-----------|------|-----|
| auth-global | Global | `Ratelimit.Global` |
| auth-register-code | IP | `Ratelimit.VerificationCode` |
| auth-register | IP | `Ratelimit.Register` |
| auth-login | IP | `Ratelimit.Login` |
| auth-password-reset-* | IP | `Ratelimit.PasswordReset` |
| auth-refresh | IP | `Ratelimit.Refresh` |
| ai-chat / stream / resume / writing | User | `Ratelimit.AIChat` |

### 13.3 输入与上传安全

- GORM 参数化查询避免 SQL 注入
- 登录/注册/评论/上传接口均有参数校验
- 上传模块检测真实内容类型（`http.DetectContentType`）而非信任客户端 MIME
- 存储路径防护（禁止 `..` 穿越）

### 13.4 HTTP 安全头部

- `X-Content-Type-Options: nosniff`
- `X-Frame-Options: DENY`
- `Referrer-Policy`
- `Permissions-Policy`
- HTTPS 时启用 HSTS

### 13.5 配置安全

- JWT 占位密钥会被拒绝启动
- OAuth、站点地址、数据库、AI Key 支持环境变量覆盖
- 敏感 Cookie Secure 标志在 release 模式下自动启用
